# Opt-in RWKV scheduling, patched into the Engine

A learner can turn on RWKV scheduling with one switch in Settings. With the switch off, Hayaki schedules Cards exactly as Upstream does. With the switch on, a review Card comes due when an RWKV model predicts that the chance of recalling it has fallen to the preset's desired retention. The Card's stored due date no longer decides when it is shown.

RWKV is a recurrent neural network. The model Hayaki uses was trained on the review logs of many Anki users and is not trained again for each learner. It reads the collection's whole review log in time order and predicts the chance that a Card is answered correctly now. FSRS models each Card from that Card's own history. RWKV also keeps state for the Card's note, deck, preset and the whole collection, so a learner's results on other Cards change its prediction. [Fushi](https://github.com/hajisensai/Fushi/tree/develop/native/fushi_rwkv) ships this model in all of its apps, and Hayaki reuses its inference crate.

## Decision

- **One patched Engine serves all three apps.** Hayaki keeps one fork of Upstream Anki at the tag the apps pin, currently `26.09.4`. The fork adds an RWKV review queue to `rslib` and links the `fushi_rwkv` crate. Android, iOS and desktop build from the same fork, so the same review log gives nearly the same predictions on every device. Predictions can differ by up to about 4e-4 between CPU types (measured by Fushi at int8), which can change whether a Card that sits right at the target is due today.
- **The patch changes which review Cards are queued, and the counts that report them.** Sync, AnkiWeb login, storage, import and export stay as Upstream wrote them. The patch adds no tables, no columns and no deck options fields.
- **The switch is one collection config key, `hayakiRwkvScheduling`.** Upstream syncs every collection config key as JSON (`rslib/src/sync/collection/changes.rs`), so the switch follows the collection to every Hayaki device, and Anki and AnkiDroid ignore it. Upstream sends the whole config map from the newer collection and replaces the older one's map, so the last device to change any config wins. A device that changed config after the switch, and syncs first, turns the switch back. Hayaki does not copy the approach of kuma3-anki-core, which adds fields 67 to 85 to the `DeckConfig` protobuf. Upstream stores deck options as a protobuf blob, and prost drops fields it does not know. An unpatched app that saves a preset it received through a full sync or a package file erases those fields, and Upstream may later give those numbers other meanings.
- **Answering a Card stays Upstream's.** FSRS or SM-2 writes the due date, interval and memory state on every answer, whether the switch is on or off. The Engine rebuilds the study queue when the switch changes, so turning it off returns to the stored due dates at once. Anki, AnkiDroid and AnkiWeb always see an ordinary collection.
- **RWKV state is derived and stays on the device.** Each device replays the synced review log into the model and keeps a snapshot beside the collection, outside `collection.anki2`. The switch is the only RWKV value that syncs.
- **Study never waits for RWKV.** While the model is downloading or replaying, or after any RWKV error, the Engine builds Upstream's queue and the app shows the RWKV status. Fushi chose the opposite and holds RWKV review Cards back until the model is ready, so that no Card is shown under both rules on one day. In Hayaki a Card answered under the fallback counts as answered today, and the RWKV rule shows it again only through the same-day guard. A short wait for the first replay is worse for a Daily Reviewer than one extra review.

## Consequences

- The Engine is no longer identical to Upstream. When the patch lands, the definition of Engine in [GLOSSARY.md](../../GLOSSARY.md) changes to say so. Each Engine update now means rebasing the patch onto the new Upstream tag and running the parity tests in the [RWKV scheduling specification](../../.scratch/rwkv-scheduling/spec.md) again.
- Android builds the Engine from source instead of taking `io.github.david-allison:anki-backend-android` from Maven. `AnkiDroid/build.gradle.kts` already accepts `local_backend=true`. Release builds need an Engine artifact that Hayaki builds from the fork.
- `fushi_rwkv` is AGPL-3.0-or-later. Hayaki for Android is GPL-3.0 and already links Upstream's AGPL `rslib`, so linking one more AGPL crate adds no new obligation. Hayaki for iOS and desktop are AGPL-3.0-or-later.
- Hayaki uses the small model (`JSchoreels/anki-rwkv`, package `sm56`) on all three apps. It needs about 3 KB of state for each Card, against about 25 KB for the large model (measured by Fushi, one Card per note), and Fushi measured it as more accurate. Hayaki does not bundle the weights. The app downloads them from the author's pinned URL when the learner first turns the switch on, as Fushi does. The repository's `WEIGHTS-NOTICE.md` (added 2026-11-20) keeps the weights outside its MIT License and limits them to personal and research use until the dataset owners settle redistribution. The owner accepted this on 2026-11-24.
- The switch ships only if RWKV predicts the owner's own review history better than the collection's FSRS parameters. Phase 0 of the specification measures this.
- This reopens the "stays identical to Upstream" part of the Engine definition. It leaves [ADR-0001](0001-own-fork-no-upstreaming.md) in force. Sync remains Upstream's code, which is the condition that ADR records for AnkiWeb access.
- A Card answered in Anki or AnkiDroid still comes due there by its FSRS date. A learner who also uses those apps sees different Cards on different apps on the same day. The collection data stays valid.
